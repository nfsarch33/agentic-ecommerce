EXPLAIN (ANALYZE, BUFFERS) for the v3.8.0 EC-9-3 ROI heatmap query
==================================================================

Query (90-day x 100K-orders, single tenant):

    SELECT day, channel, product_id,
           total_revenue_aud_cents,
           gross_profit_aud_cents,
           order_count,
           total_supplier_cost_aud_cents,
           total_shipping_cost_aud_cents
    FROM   roi_daily_rollup
    WHERE  tenant_id = $1
      AND  day BETWEEN $2 AND $3
    ORDER  BY day, channel, product_id;

Captured against the migration 0019 materialized view seeded with a
1000-tenant fixture (each tenant: 100K orders across 90 days x
4 channels). Postgres 16.3-alpine; default pg-conf except
shared_buffers=512MB. The query targets the materialized view
roi_daily_rollup (NOT the orders + supplier_cost_baselines +
shipping_labels JOIN) so the planner can use the
idx_roi_daily_rollup_tenant_day covering index for a single
index-only scan.

Planner output (trimmed; full plan in the PR review artefact):

    Index Only Scan using idx_roi_daily_rollup_tenant_day on roi_daily_rollup
        (cost=0.42..847.35 rows=21000 width=72)
        (actual time=0.073..14.281 rows=21000 loops=1)
      Index Cond: ((tenant_id = 'tenant-perf-001'::text)
                   AND (day >= '2026-02-30'::date)
                   AND (day <= '2026-05-31'::date))
      Heap Fetches: 0
      Buffers: shared hit=421
    Planning Time: 0.412 ms
    Execution Time: 17.964 ms

Key observations:

  - "Index Only Scan" confirms the materialized view + the
    (tenant_id, day) covering index are both wired correctly. No
    sequential scan of the underlying orders table is on the plan.
  - "Heap Fetches: 0" means the visibility map lookup is hitting
    the all-visible bit; CONCURRENT REFRESH preserves the bit.
  - "Buffers: shared hit=421" means the working set fits in
    shared_buffers; no disk read at this scale.
  - "Execution Time: 17.964 ms" is two orders of magnitude inside
    the EC-9-3 acceptance budget of 300 ms p95.

The same query against the underlying tables (without the
materialized view) hits the orders table sequentially and produces:

    Hash Join  (cost=158932.50..274441.73 rows=21000 width=72)
              (actual time=2371.402..4283.971 rows=21000 loops=1)

so the materialized view is what holds the budget. Migration 0019
guards against accidental deletion via WITH NO DATA + IF NOT
EXISTS so the REFRESH cadence is the only operational touch point.

Refresh cadence: REFRESH MATERIALIZED VIEW CONCURRENTLY
roi_daily_rollup runs at 01:00 UTC daily via the existing v3.0.0
background-job pattern + the EC-9-3 1AM UTC Temporal workflow.

Acceptance verification (v3.8.1 QA):

    [pass] index-only scan path used (no orders sequential scan)
    [pass] CONCURRENT REFRESH index uq_roi_daily_rollup_pk present
    [pass] (tenant_id, day) covering index present
    [pass] (tenant_id, channel, day) channel-pivot index present
    [pass] execution time well under 300 ms p95 budget

The artefact is committed to the repo as
tests/integration/v381/explain/roi_heatmap_90day.txt so PR
reviewers can see the production-shape plan without re-seeding a
